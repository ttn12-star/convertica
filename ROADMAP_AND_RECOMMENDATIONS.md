## Конвертация / API / Celery
- **`pdf_to_jpg`**
  - Исправлен критичный баг в [convert_pdf_to_jpg_sequential](cci:1://file:///home/nkdev/convertica/utils_site/src/api/pdf_convert/pdf_to_jpg/utils.py:50:0-238:37): раньше список `images` затирался и ZIP мог получаться пустым/ломаться.
  - Переведено на **memory-friendly** режим `pdf2image` через `paths_only=True` + `output_folder=...` (не держим PIL-изображения в памяти).
  - Добавлены/усилены проверки: диск (`check_disk_space`), пустой PDF.
  - [convert_pdf_to_jpg](cci:1://file:///home/nkdev/convertica/utils_site/src/api/optimization_manager.py:252:0-254:81) теперь корректно работает в sync-контексте через `async_to_sync(optimization_manager.convert_pdf_to_jpg)` и передаёт `pages/dpi`.

- **[generic_conversion_task](cci:1://file:///home/nkdev/convertica/utils_site/src/tasks/pdf_conversion.py:45:0-376:16) (Celery)**
  - **Сильно снижено потребление RAM**: больше не читаем входной файл целиком (`f.read()`), используем потоковый `File(...)`.
  - **Унифицирована фильтрация kwargs**: вместо ручного `valid_kwargs` теперь фильтрация по `inspect.signature` — меньше шансов “сломали параметр при оптимизации”.
  - Исправлен баг с tuple-результатом: в общем случае теперь корректно берём `output_path` из `(input_path, output_path)`.
  - Усилен `finally`: безопасное закрытие файлового дескриптора.
  - `SoftTimeLimitExceeded`: теперь возвращаем понятную ошибку и не удаляем критичные файлы так, чтобы ретраи ломались.

- **`pdf_to_word_optimized`**
  - `ocr_language` теперь реально используется в optimized OCR-потоке (приоритетнее языка из request, если не `"auto"`).
  - Зафиксирован класс ошибок “съехали аргументы” (позиционные вызовы заменены на keyword args в обёртке).

- **`word_to_pdf_optimized`**
  - Убраны позиционные аргументы в wrapper (переведено на keyword args), чтобы не ловить “съехали параметры” при будущих изменениях сигнатур.

  - light: merge/split/rotate/organize
  Это улучшит latency лёгких задач под нагрузкой.

## Этап 3 (масштабирование “добавлением ресурсов”)
- На 8GB:
  - можно пробовать `--concurrency=2` для regular воркера
  - включить `celery-premium` профилем и дать ему отдельные ресурсы
- На 16GB:
  - `--concurrency=3-4`
  - отдельные воркеры: premium-heavy / regular-heavy / light

# Сколько пользователей выдержим сейчас (оценка)

Точно посчитать без метрик нельзя, но можно дать реалистичную оценку по текущей архитектуре:

## Ограничивающий фактор
- **Celery worker `--concurrency=1 --pool=solo`** ⇒ в любой момент выполняется **1 тяжёлая задача** на воркере.
- Значит “пропускная способность” считается как **задачи/час**, а не как “пользователи/сек”.

## Примерные порядки (на 4GB/2vCPU, без OCR)
- **Лёгкие операции (merge/split/rotate, небольшие PDF)**: десятки–сотни задач/час.
- **PDF→JPG (10–20 стр, dpi 200–300)**: условно 10–30 задач/час (очень зависит от PDF и poppler).
- **PDF→Word (pdf2docx)**: условно 3–15 задач/час (зависит от сложности документа).
- **OCR**: самый дорогой путь; может легко “съесть” очередь.

## По пользователям
Если средний пользователь делает 1 тяжёлую конвертацию:
- при 10 тяжёлых задачах/час это **~10 активных “тяжёлых” пользователей в час** без заметных очередей,
- при всплесках очередь будет расти линейно.

Чтобы выдерживать “много пользователей” без ожидания — нужно либо:
- включать второй воркер (или `celery-premium`)  
- или увеличивать сервер и concurrency  
- или дробить heavy/light очереди
